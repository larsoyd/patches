I had been chasing an intermittent KDE Plasma Wayland bug where taskbar window previews would sometimes stop working and PipeWire would report errors like `no more input formats`. What made it especially annoying was that it could disappear after a logout, reboot, or Plasma restart, which made it look like some vague NVIDIA, PipeWire, KWin, or Wayland instability.

I started by ruling out the obvious things. The NVIDIA kernel module and userspace versions matched, PipeWire and WirePlumber were healthy, the portal setup looked normal, and there were no matching kernel-side NVIDIA, DRM, DMA-BUF, or GPU errors when the thumbnail failure happened. I also confirmed that ordinary screen recording still worked, which was a useful clue because it meant this was not a general KWin-to-PipeWire capture failure. The problem seemed much narrower, specifically around the Plasma Task Manager thumbnail path using KPipeWire.

The first really useful breakthrough came from capturing an actual failed PipeWire negotiation instead of reasoning from the error message alone. KWin's output side was offering only `BGRA` and `BGRx`, while the Plasma/KPipeWire input side was advertising `RGB`, `xBGR`, `RGBA`, `RGBx`, `BGR`, `GRAY8`, and `ABGR`. The two formats KWin needed, `BGRA` and `BGRx`, were completely absent from the input side. That meant the `no more input formats` error was literal: the producer and consumer had no common pixel format.

That raised the next question: why were `BGRA` and `BGRx` missing when KPipeWire's source clearly supports them? I cloned the Arch package repository and inspected the exact KPipeWire 6.7.4 source used by the PKGBUILD rather than just looking at current upstream. In `pipewiresourcestream.cpp`, KPipeWire intends to advertise nine formats: `RGBx`, `RGBA`, `BGRx`, `BGRA`, `RGB`, `BGR`, `xBGR`, `ABGR`, and `GRAY8`. For each format, when DMA-BUF modifiers are available, it builds one format object with modifiers and another without modifiers, so the full intended list can contain eighteen SPA POD objects.

While reading that code I noticed two fixed `uint8_t buffer[4096]` allocations, one for initial stream setup and another for renegotiation. Both were backing the SPA POD builder used to construct those format parameters. That immediately became suspicious because the failed PipeWire dump contained exactly fourteen format objects, or seven complete modifier/no-modifier pairs, even though the source intended nine formats.

The object sizes in the failed log made the suspicion much stronger. Every modifier-bearing format object had a body size of 336 bytes, and every modifier-less object had a body size of 192 bytes. Seven complete pairs therefore accounted for 3696 bytes of object bodies. Adding the 8-byte SPA POD header for each of the fourteen objects brought the real builder usage to exactly 3808 bytes. That left only 288 bytes free in a 4096-byte buffer. The next modifier-bearing object needed another 344 bytes including its header, which would move the builder offset to 4152. In other words, the eighth format physically could not fit.

I did not want to stop at arithmetic that merely looked convincing, so I wrote a standalone test using the real installed libspa and libpipewire 1.6.8 headers and copied KPipeWire's actual `buildFormat()` logic into it. That reproduced the real runtime sizes exactly: 192 bytes for a plain format object and 336 bytes for a modifier-bearing one with the modifier count my system was exposing. Packing seven complete pairs into a real 4096-byte `spa_pod_builder` landed at exactly 3808 bytes, and attempting the eighth modifier-bearing object pushed the offset to exactly 4152 and failed. That removed a lot of uncertainty because the runtime logs, the source code, and the real SPA implementation were now all agreeing to the byte.

I then dug into why exactly two complete formats disappeared instead of getting some random partial corruption. Once the SPA builder's offset passes the end of the fixed buffer, the builder state remains beyond capacity, so later constructions using the same builder fail as well. The eighth format overflows, then the ninth fails too. KPipeWire later calls `params.removeAll(nullptr)`, so those failed format builds are silently thrown away. The result is a perfectly clean-looking but truncated capability list: nine formats intended, seven formats advertised, two formats gone.

The remaining mystery was why the particular missing pair seemed to change between Plasma launches. KPipeWire stores the format-to-modifier mapping in a `QHash` and iterates that hash when constructing the PipeWire parameters. Qt does not guarantee insertion order for `QHash`, and its hashing is salted with a per-process seed. That means the same nine formats can be visited in a different order each time `plasmashell` starts. The first seven happen to fit, while the last two are lost after the buffer overflows.

I tested that directly too. I wrote another harness reproducing the actual `QHash<spa_video_format, QList<uint64_t>>`, populated it with the same format set, and launched it as one hundred separate OS processes so each run got a fresh hash seed. Every single run dropped exactly two formats and preserved exactly seven. What varied was which two got dropped. Some runs lost `BGR` and `RGBx`, some lost `RGBA` and `ABGR`, some lost other pairs, and a few runs lost exactly `BGRA` and `BGRx`, which matched the broken Plasma session I had captured. That explained why restarting Plasma could make the bug appear to vanish without actually repairing anything.

I also found an old KDE bug that made the whole thing even more convincing. KDE had already hit essentially the same failure class years earlier. At that time the buffer was only 1024 bytes, and long DMA-BUF modifier lists could exhaust it and break PipeWire negotiation. The fix was simply to raise the buffer from 1024 to 4096. That was a major clue because the current failure was not some unrelated NVIDIA oddity. It was the same basic scalability problem returning after the format set and modifier data had grown enough to exhaust the newer 4096-byte limit too.

The most satisfying test came when I captured a session where thumbnails were currently working. If the theory was correct, a working session should still be overflowing the 4096-byte builder. It should just be dropping two harmless formats instead of the two KWin needed. I wrote a small loop that waited for the temporary taskbar thumbnail PipeWire nodes to appear while I hovered a taskbar entry and immediately dumped their live `EnumFormat` parameters.

That working, unpatched session showed exactly fourteen objects and exactly seven distinct formats again. The surviving formats were `RGBx`, `RGB`, `BGRA`, `RGBA`, `BGRx`, `GRAY8`, and `BGR`. The two missing formats were `xBGR` and `ABGR`. At the same time, KWin was still offering only `BGRA` and `BGRx`. So the overflow was absolutely still happening while the feature looked healthy, but this time the hash ordering had allowed both of KWin's required formats to survive. That was the clearest explanation for the apparent intermittency: the underlying bug was always there, but only some process hash seeds made it user-visible.

At that point I created a proper local Arch patch changing both relevant `uint8_t buffer[4096]` declarations to `uint8_t buffer[16384]`. I deliberately changed nothing else. I did not alter KWin, PipeWire, DMA-BUF support, format ordering, the `QHash`, or the Task Manager QML. The only functional change was giving KPipeWire enough storage to serialize the formats it was already trying to advertise.

After installing the patched build, I repeated the exact same live PipeWire capture. This time the Plasma input node exposed eighteen `EnumFormat` objects and all nine intended formats. Nothing was missing. `RGBx`, `RGBA`, `BGRx`, `BGRA`, `RGB`, `BGR`, `xBGR`, `ABGR`, and `GRAY8` were all present. KWin was still offering the same `BGRA` and `BGRx` pair as before, so the producer side had not changed. The only difference was that KPipeWire was no longer truncating its own input format list.

The before-and-after result was very clean. Unpatched, the builder had 4096 bytes available while the current serialized format set required about 4896 bytes, so only fourteen objects and seven formats survived. Patched, the same 4896 bytes fit comfortably inside 16384, so all eighteen objects and all nine formats appeared. The random QHash ordering still existed, but it no longer mattered because every format could fit regardless of order.

I also learned something important from the fix itself. Raising the limit to 16384 solves my machine's concrete problem and gives a lot of headroom, but it is not the ideal upstream design. KDE already went from 1024 to 4096 once because the old fixed size became too small. The amount of data being serialized depends on the number of supported formats and on driver-provided DMA-BUF modifier lists, so it is fundamentally variable-sized data. A proper upstream fix should probably calculate the necessary storage from the actual format and modifier lists, or use dynamically managed POD storage in a way that avoids invalidating stored pointers. KPipeWire should also detect builder exhaustion explicitly instead of silently deleting the failed PODs and turning a buffer overflow into a confusing, intermittent `no more input formats` error.

The part I'm happiest with is that I did not stop at “I made the buffer bigger and the bug disappeared.” I reproduced the exact byte sizes using the real SPA implementation, proved the 4096-to-4152 overflow boundary, reproduced the two-format loss across one hundred separate process seeds, caught both a broken and a working unpatched Plasma session, showed that both were internally truncated in different ways, and then repeated the same live capture after the patch and saw the list go from seven out of nine formats to nine out of nine. That turned a frustrating intermittent desktop glitch into a fully explained, reproducible root cause.
